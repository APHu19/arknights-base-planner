## 3. 已固化的数值（改动前务必三思）

- 赤金 4320s/枚；源石碎片 3600s/片；中级作战记录 1000 经验/10800s
- 订单：`(2赤金,1000币,2:24,30%)(3,1500,3:30,50%)(4,2000,4:36,20%)` → **币/赤金恒 500**
- 但书违约：`合同法` + `违约索赔·α/+1，·β/+2`，龙门币**同比例放大** → 解析解 6.64 币/效率点·h、0.01327 赤金/效率点·h
- 品质分布（实测，精确复现）：常规 (30,50,20)／α (15,30,55)／α×2 (13,22,65)／β 与 α+β (5,10,85)；
  慢热线性：α 3h、β 5h 满档
- 电力：发电站 Ⅰ/Ⅱ/Ⅲ = 60/130/270；制造·贸易 = 10/30/60；固定房间（会客60+办公10+加工60+训练60+**宿舍0**）= 190
  （旧口径 450 把 4×宿舍按 65 计；GUI 可切）→ **252 必须给部分制造站降到 Ⅱ 才能平衡**
- 无人机：全局 10 架/h；1 架 = 3 分钟基础耗时（金站 0.0417 枚 / 碎片站 0.05 片 / 玉站 0.5 玉且吃 0.05 片）

## 4. 心情模型（最容易错的地方）

- 消耗 = `1.0 − 0.05×(人数−1)` + 自身修正 + 房间级修正 + **房间“其他干员”修正（不含自己）** − 中枢减压
- 中枢减压**取最高**（公事公办 / 孤光共照 / 巴别塔之帜），不是相加；另加 0.05×中枢人数
- 宿舍恢复 = 4.0/h + 该房间**最高**的“所有干员恢复+X”（按人头各算，不摊分）
- 控制中枢三人组（阿米娅/凯尔希/重岳）必须**两段轮休**（第 3、6 班）；重岳自身 +0.5/h 只作用本人
- 菲亚梅塔：`order: "pre"`；每天最多 2 次交换，只挑最缺心情的在岗者
- 寝室用**恢复债**（累计消耗−累计恢复）分配，不要用"当前心情最低优先"（会饿死慢速消耗者）

## 5. 求解器结构

`候选池(按优先级排序，不是硬分层) → 束搜索(多排序混合：原始产出/扣惩罚/产出耗金比) → 用全局目标择优
→ 体系资源不动点迭代 → 预算约束修复(赤金/碎片按产出封顶，组合选择) → 2-opt 局部搜索 → 固定房间预设枚举`

**为什么不用影子价格**：所有订单档币/赤金恒为 500，给赤金定价只是等比缩放，无法区分方案 → 必须用**预算组合选择**。

## 9. 下一步核心改造：干员级窗口排班（把心情闭环做成枚举期约束）

**目标**：排班必须**长期可持续**——任意干员在两次上班之间的休息足以撑过下一次工作窗口（唯一验收标准：
00:00 满心情起算，次日 00:00 回满，见 `core/daycheck.py`）。

**关键算术（先算清再写代码）**

| 项 | 值 |
| --- | --- |
| 每班在岗 | ≈30 人（制造 3×3 + 贸易 3×3 + 发电 3×3 + 中枢 5 + 会客 2 + 办公 1 + 加工 1） |
| 每日岗位工时 | 30 × 6 班 × 4h = **720 干员·小时** |
| 床位 | 4 间 × 5 = **20** ⇒ 每班不在岗 ≤20 ⇒ 唯一干员 **N ≤ 50** |
| 单人可持续上限 | N=50 ⇒ 每人 **14.4h/天** + 休息 9.6h：消耗 14.4×0.9≈13 ＜ 恢复 9.6×4.2≈40 ✔ |
| 结论 | **紧约束但可行**（此前"60 人下限"是因为误设每人只能 12h） |

**不能靠"A/B 合并"压人数**（已实测失败：合并 → 该站 24h 常驻 → 无休息窗口 → 闭环 −6.4 恶化到 −12.6）。

**正确模型：按“实际时间窗口”排，不引入 G 这种抽象**（用户明确纠正）
- 班次表是**任意真实区间**（例：6,6,12 三班 = [0,6) [6,12) [12,24)），直接按这些区间排，不存在"轮换组数 G"的预设
- 对每个候选安排，**当场计算寝室容纳可行性**：
  ① 每个区间的不在岗人数 ≤ 20（床位）；② 每个干员的休息区间够不够撑过下一段工作；③ 次日 00:00 是否回满
- **不可行就换分组重新枚举**（而不是硬套 ABC/AB 模板）；干员可跨设施分班，ABC/AB/6组只是某些可行解的**表现形式**
- **不允许常驻**（用户定）：G=1 这类无休息窗口的安排直接排除

**算法骨架（`solve/schedule.py` 原型）**
```
1. 把班次表折算成真实区间列表 W = [(t0,t1), …]（可不等长）
2. 先按“岗位价值”排序所有 (房间, 区间) 需求
3. 依次为每个需求挑队伍：候选 = 该房间合格且“本区间空闲”的干员
4. 对每个候选做**增量可行性判定**（核心，心情检查内嵌）：
     把该干员放进本区间 → 重算他当天的 工作/休息 窗口 → 要求
        · 任一工作窗口内不被消耗光
        · 次日 00:00 回到满心情
        · 本区间不在岗人数（含新安排）≤ 20 且他有床位
     任一不满足 → 该候选不可行，换下一个
5. 全部需求排完后，用 core/daycheck.py 做**终检**；若失败 → 调整分组/换人重排（回到 3），
   记录失败原因（是"床位不够"还是"恢复不足"），据此决定是缩人数还是拆窗口
```
**落点**：新增 `solve/schedule.py`，替换 `plan.py` 的 `build_shifts/solve_dorms`；开关 `--sched ab|window`
（默认 ab 保持现状），`core/daycheck.py` 是**唯一验收器**。顺带天然解决"非 4h 班次适配"。

**落点**：新增 `solve/schedule.py`（贪心 + 局部调整：先按岗位价值排序，再按"谁还能接这班且闭环成立"选人），
替换 `plan.py` 的 `build_shifts/solve_dorms`；开关 `--sched ab|window`（默认 ab 保持现状），
`core/daycheck.py` 是**唯一验收器**（两条路径都必须过）。顺带天然解决"非 4h 班次适配"。

## 10. window 调度器：已实现的部分与**实测出的两个结构性障碍**（2024 会话新增）

**已实现**：`solve/schedule.py`（判定核 + 单房间排班；**尚未接进求解器/默认路径**）、
`probe_sched.py`（验收脚本，跑 6,6,12）。API 速查：

```
st = SCH.DayState(hours=[6,6,12], ds=ds, policy='literal'|'steady',
                  targets={区间: 计划在岗人数}, parked=[常驻宿舍干员], rest_slots=[纯休息区间])
SCH.schedule_room(st, '制造站', inst=2, product='Pure Gold', level=3, need=3, slots=[0],
                  pool=候选池, rank=排序函数, avail_filter=候选预滤, topn=8, combo_cap=120)
SCH.pack_dorms(st, ds, leads=[恢复技干员]);  SCH.verify(st, ds)   # → daycheck 原始结果 + 对账
```
判定顺序（`can_place`）：区间冲突 → 容量 → **常驻**（加上本区间就全天无休 → 判死）→
**床位**（N ≤ 20 + 该区间计划在岗人数，逐区间查）→ **心情**（按 policy 投影当天/稳态时间线）。
实测 `预测/终检对账 max_abs_diff = 0.0`（事前预测与 daycheck 逐人一致，可放心用它做枚举期剪枝）。

**判据已裁定为 A（长期稳态）**：`core/daycheck.py` 的默认 `criterion='steady'`，`report` 形如
`判据A(长期稳态) ✔ 4 天迭代后无人被打穿，稳态最低心情 7.50（≥ 1）［诊断·字面口径：32/52 人在次日 00:00 未回满］`。
`morale_day(shifts, ds, criterion='literal')` 仍可切到字面口径（**只作诊断**）。返回字典里两个口径都在：
`steady_ok/steady_failures/steady_lows/steady_end/steady_windows` 与
`literal_ok/literal_failures/literal_lows/literal_end`；旧键（`ok/end/lows/failures/windows/log`）= 当前生效口径。

**两个结构性障碍（判据 B/literal 不可达的原因，不是排班技巧问题）**
1. **时间**：任何在跨/贴 00:00 的区间在岗者，00:00 必然 < 24 ⇒ 24h 全覆盖表在 `literal` 下**必 ✘**
   （6,6,12 的第三段 [12,24)：实测 −9.00 ~ −19.50）。
2. **床位**：末段只有 **20 张床**，而"最后一班在岗"是 **32 人**；拿不到床的人 00:00 回不满
   （实测恰好 **−4.50/人**：中枢 5 人房 0.75×6h）。⇒ 即使把末段整段设为纯休息班（6,6,6,6）仍 ✘。
   **要过 literal 只能**：① 最后一班在岗 ≤ 20 人；② 允许区间内轮床（床位当共享资源按时长折算）。

**判据 A 实测（6,6,12，`probe_sched.py` 场景 B）**：三班各 32 人在岗、床位占用正好 20/20、
**稳态 52/52 通过**（最低 7.50）、工作量分布 8×6h＋12×12h＋32×18h、**无 24h 常驻**；
"硬把尾班补满"（场景 A2）会造出 24h 常驻 ⇒ 判据 A 也 ✘（8/72 人最低 0.00），说明 A 并非无脑放行。

**枚举里踩过的三个坑（别再踩）**
1. 候选排序要**先摊人**（load 升序），不要"在册优先"——后者会让同几个人连排到 18h，后面区间反而没人可用；
2. 枚举顺序要**区间优先**（先排满第 1 班再排第 2 班），房间优先会让"必然排不出的尾班"先吃掉床位名额；
3. 床位满员后要在**候选层**就排除"新人"（名额要按整队 need 预留），否则枚举会在几百个必然被拒的候选上空转。
